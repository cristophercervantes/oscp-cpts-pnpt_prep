### **DNS Zones 

DNS zones are portions of the DNS namespace that are managed by a specific organization or administrator. They contain all the DNS records for a particular domain or subdomain.

#### **Primary DNS Server (Master)**

- Holds the **original, authoritative** copy of the zone file.
- All DNS records for the domain can only be **created or edited** here.
- This is the single source of truth for the zone.
- When changes are made, the primary server pushes updates to secondary servers.

#### **Secondary DNS Server (Slave)**

- Holds a **read-only copy** of the zone file from the primary server.
- Acts as a **backup** and provides redundancy.
- Periodically checks with the primary server to sync updates.
- If the primary server goes down, secondary servers can still answer DNS queries.

**Key Point**: A zone can have **only one primary** server but **many secondary** servers.

#### **Zone Files**

Zone files are the actual databases that store DNS records for a domain.

There are two types:

- **Primary Zone** (Master) → Editable copy on the primary server.
- **Secondary Zone** (Slave) → Read-only copy on secondary servers.

The process of copying the zone from primary to secondary is called a **Zone Transfer**.

Think of it like this:

- The TLD (e.g., .com) is like a department manager.
- Each domain (e.g., inlanefreight.com) is a team leader.
- Subdomains (www, mail, blog) are individual team members.

#### **Types of Zone Transfers**

1. **AXFR (Asynchronous Full Transfer)**
    - Transfers the **entire** zone file.
    - Used for initial sync or full refreshes.
2. **IXFR (Incremental Zone Transfer)**
    - Transfers **only the changes** since the last update.
    - More efficient for frequent small updates.

#### **Security Concern: Zone Transfer Misconfiguration**

By default, DNS does **not** require authentication for zone transfers.

If an administrator does **not** restrict which servers/IPs are allowed to request zone transfers, **anyone** can request a full copy of the zone file using AXFR.

This is a **serious information disclosure** risk because it reveals:

- All hostnames
- All IP addresses
- Internal network structure
- Mail servers, name servers, etc.

Attackers can map the entire network and discover hidden hosts/subdomains that were not meant to be public.

Many organizations still have misconfigured DNS servers that allow unrestricted zone transfers — this is a common finding during penetration tests.

### **DNS Records and Queries 

DNS records are the actual instructions stored on authoritative name servers. They tell the DNS system how to handle requests for a domain — such as which IP address to return, where to send email, or which server is authoritative.

These records are what make DNS work behind the scenes.

#### **Most Common DNS Records**

Here are the records you will encounter most often during penetration tests and enumeration:

|Record Type|Full Name|Purpose|
|---|---|---|
|**A**|IPv4 Address Record|Maps a domain name to an IPv4 address|
|**AAAA**|IPv6 Address Record|Maps a domain name to an IPv6 address|
|**CNAME**|Canonical Name Record|Creates an alias (one name points to another name)|
|**MX**|Mail Exchanger Record|Specifies mail servers for the domain|
|**NS**|Name Server Record|Specifies the authoritative name servers for the domain|
|**PTR**|Pointer Record|Used for reverse DNS lookups (IP → domain name)|
|**SOA**|Start of Authority Record|Contains administrative info about the zone (primary name server, serial number, refresh timers, etc.)|
|**TXT**|Text Record|Stores arbitrary text, commonly used for SPF, DMARC, and domain verification|

Other records exist (HINFO, ISDN, etc.), but the ones above are the most relevant for pentesters.

#### **Tools for DNS Queries**

The two most common tools for querying DNS are:

- **dig** – Powerful, detailed, and widely used in Linux environments
- **nslookup** – Simpler, available on both Windows and Linux

#### **Important Queries**

**1. NS Records (Name Servers)** Finds the authoritative name servers for a domain.
```
dig NS inlanefreight.com
```

**2. SOA Record (Start of Authority)** Shows administrative details about the zone.
```
dig SOA inlanefreight.com
```

**3. TXT Records** Often contains SPF, DMARC, or other security-related information.
```
nslookup -type=txt inlanefreight.com
```

**Example SPF Record:**
```
nslookup -type=SPF inlanefreight.com
# Output might show: v=spf1 include:_spf.google.com ...
```

**Example DMARC Record:**
```
nslookup -type=txt _dmarc.inlanefreight.com
# Output: v=DMARC1; p=reject; ...
```

#### **Info In Pentest**

- **NS Records** → Help identify name servers that might allow zone transfers
- **MX Records** → Reveal mail servers (useful for phishing or SMTP attacks)
- **TXT Records** → Often leak SPF/DMARC policies or verification tokens
- **A/AAAA Records** → Give direct IP addresses of hosts and subdomains
- **CNAME Records** → Can reveal internal hostnames or third-party services

During enumeration, you will frequently query these records to map the target’s infrastructure and discover hidden or misconfigured assets.

### **DNS Security 

DNS is one of the most critical parts of any network — every connection starts with a DNS lookup. Because of this central position, DNS has become both a **major vulnerability** and a **powerful security control point**.

Many organizations now treat DNS as an active layer of defense instead of just a naming service.


- DNS is involved in **every** network request.
- It can act as a central checkpoint to detect and block malicious activity.
- DNS security integrates well with other tools:
    - Threat intelligence feeds
    - EDR (Endpoint Detection and Response)
    - SIEM (Security Information and Event Management)
    - Firewalls, proxies, NAC, and vulnerability scanners

By sharing Indicators of Compromise (IOCs) and Indicators of Attack (IOAs), DNS security helps coordinate faster incident response across the entire security stack.

#### **DNSSEC – Domain Name System Security Extensions**

DNSSEC is the main standard designed to protect the **integrity and authenticity** of DNS data.

**Goal of DNSSEC:**

- Ensure the DNS response you receive has not been tampered with (no man-in-the-middle attacks).
- Verify that the data actually comes from the legitimate authoritative source.

**How DNSSEC Works:**

- Uses **digital signatures** based on public-key cryptography.
- The authoritative DNS server signs its records using a **private key**.
- Clients verify the signature using the corresponding **public key**.

**DNSSEC Concepts:**

- **Private Key** (Zone Signing Key):
    - Kept secret by the DNS server that manages the zone.
    - Used to digitally sign all resource records (A, MX, NS, etc.).
    - Each zone has its own set of keys.
    - Keys have expiration dates and are rotated over time.
- **Public Key** (DNSKEY record):
    - Published in the zone so anyone can verify the signatures.
    - Used by resolvers and clients to check if the received data is authentic and untampered.
- **RRSIG Record**:
    - A new record type introduced by DNSSEC.
    - Contains the digital signature for each DNS record.

**Important Requirement:** Both the DNS provider (authoritative server) **and** the client/resolver must support DNSSEC for it to work end-to-end.

When DNSSEC validation succeeds:

- You can be confident the response is genuine.
- Manipulation or spoofing of DNS data becomes extremely difficult.
