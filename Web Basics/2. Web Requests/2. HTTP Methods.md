## HTTP Methods and Status Codes

HTTP methods define the **action** the client wants to perform, while status codes provide the **result** of that action from the server's perspective.

### 1. HTTP Request Methods

While `GET` and `POST` are the most common, modern web applications and REST APIs utilize a wider range of methods to manage resources.

|**Method**|**Purpose**|**Key Detail**|
|---|---|---|
|**GET**|Retrieve a resource.|Data is passed in the URL (query strings).|
|**POST**|Submit data to the server.|Data is sent in the request body (forms, file uploads).|
|**HEAD**|Retrieve headers only.|Same as GET but returns no response body; used to check file size or existence.|
|**PUT**|Create/Replace a resource.|Often used in APIs to upload a specific file or update a full record.|
|**PATCH**|Partial modification.|Used to update only specific fields of a resource.|
|**DELETE**|Remove a resource.|Deletes the specified file or data entry.|
|**OPTIONS**|Check server capabilities.|Returns a list of HTTP methods supported by the server.|

### 2. HTTP Status Codes

Status codes are three-digit integers divided into five distinct classes. They tell the client whether the request was successful, redirected, or encountered an error.

#### The Five Classes:

- **1xx (Informational):** The request was received, and the process is continuing.
    
- **2xx (Success):** The action was successfully received, understood, and accepted (e.g., **200 OK**).
    
- **3xx (Redirection):** Further action is needed to complete the request (e.g., **302 Found** for temporary redirects).
    
- **4xx (Client Error):** The request contains bad syntax or cannot be fulfilled (e.g., **403 Forbidden** or **404 Not Found**).
    
- **5xx (Server Error):** The server failed to fulfill an apparently valid request (e.g., **500 Internal Server Error**).

### 3. Common Status Codes in Security Testing

As a penetration tester, these codes provide immediate feedback on the application's behavior:

- **200 OK:** Standard success response.
    
- **301/302 Redirect:** Often seen during successful logins or when a page has moved.
    
- **401 Unauthorized:** The request requires user authentication.
    
- **403 Forbidden:** The server understood the request but refuses to authorize it. This often triggers when a Web Application Firewall (WAF) blocks a malicious payload.
    
- **404 Not Found:** The requested resource is missing. Useful during **directory brute-forcing**.
    
- **500 Internal Server Error:** Often indicates a crash in the back-end code, which can sometimes be exploited for **information disclosure** or **Remote Code Execution (RCE)**.

## HTTP GET and Authentication

In web penetration testing, the **GET** method is the primary way to retrieve resources. While it is often used to simply load a page, it is also frequently used to send data to the backend via URL parameters.

### 1. HTTP Basic Authentication

Unlike modern login forms that use POST requests and cookies, **HTTP Basic Auth** is a legacy authentication method handled directly by the web server (like Apache or Nginx) to protect a directory or file.

- **Mechanism**: When you access a protected page, the server responds with a `401 Authorization Required` status and a `WWW-Authenticate: Basic` header.
    
- **The Credentials**: The browser prompts for a username and password. These are then combined into a single string (`username:password`), **Base64 encoded**, and sent in the `Authorization` header.
    
- **Vulnerability Note**: Since Base64 is an encoding, not encryption, Basic Auth is extremely insecure over standard HTTP because anyone sniffing the traffic can instantly decode the credentials.
    
### 2. Authenticating with cURL

There are three main ways to handle Basic Auth using `cURL`:

1. **The `-u` Flag**: Automatically handles the encoding and header creation.
    ```
    curl -u admin:admin http://<SERVER_IP>:<PORT>/
    ```
    
2. **In-URL Credentials**: Passing the credentials directly in the URL string.
    ```
    curl http://admin:admin@<SERVER_IP>:<PORT>/
    ```
    
3. **Manual Header Construction**: Using the `-H` flag to send the pre-encoded Base64 string. This is useful for testing how the server handles specific header inputs.
    ```
    # 'YWRtaW46YWRtaW4=' is 'admin:admin' in Base64
    curl -H 'Authorization: Basic YWRtaW46YWRtaW4=' http://<SERVER_IP>/
    ```
    
### 3. Analyzing GET Parameters

GET parameters are data values appended to the URL after a question mark (`?`). In a "City Search" function, entering a term might trigger a request like: `http://<SERVER_IP>/search.php?search=london`

#### Monitoring with DevTools:

- **Network Tab**: Essential for seeing these background requests. When you perform a search, a new entry appears showing the specific script being called (`search.php`) and the parameters sent.
    
- **Copy as cURL**: A powerful feature in DevTools. Right-click any request in the Network tab and select **Copy > Copy as cURL**. This gives you a ready-to-use command in your terminal that includes all necessary headers and authentication tokens.
    
### 4. Testing via Console (Fetch)

You can also re-trigger these requests directly in the browser's **Console** tab using the `fetch()` API. This is helpful for testing how the frontend handles different backend responses without refreshing the entire page.

- **Process**: Copy the request as **Fetch**, paste it into the Console (`Ctrl+Shift+K`), and execute. The browser will perform the request using your current session's authentication.
    

In a web assessment, always clear your Network tab (using the trash icon) before performing an action. This ensures you isolate exactly which request is responsible for a specific function, such as a search or a data submission.

## HTTP POST and Session Management

While `GET` is used for retrieving data, **POST** is the standard method for sending data to a server, such as submitting a login form, uploading a file, or sending a JSON object to an API.

### 1. Why Use POST Over GET?

Unlike `GET`, which appends data to the URL, `POST` carries data in the **HTTP Request Body**. This offers three critical advantages:

- **Security (Lack of Logging):** URL parameters are often logged by web servers, proxies, and browser history. POST data is kept out of the URL, preventing sensitive info like passwords from appearing in logs.
    
- **Data Volume:** URLs have character limits (typically ~2,000 characters). POST bodies can handle much larger datasets, including high-resolution images or large documents.
    
- **Binary Data:** POST can handle raw binary data (like a `.zip` or `.pdf` file), whereas GET requires complex encoding to fit binary data into a URL string.
    
### 2. Login Forms and Cookies

Most modern login forms use a POST request. When you submit your credentials, the server validates them and, if correct, responds with a **Session Cookie**.

- **Set-Cookie Header:** The server sends this header (e.g., `Set-Cookie: PHPSESSID=abc123...`) in its response.
    
- **Persistence:** Your browser stores this cookie and automatically attaches it to every future request to that same server. This is how the website "remembers" you are logged in.
    
### 3. Using cURL for POST and Cookies

As a penetration tester, you must be able to simulate these browser actions manually:

**Sending POST Data:** Use `-X POST` to set the method and `-d` to provide the data string.
```
curl -X POST -d 'username=admin&password=admin' http://<SERVER_IP>/login.php
```

**Following Redirects:** Many logins redirect you to a `/dashboard`. Use `-L` to tell cURL to follow that redirect automatically.
```
curl -L -X POST -d 'user=admin&pass=admin' http://<SERVER_IP>/login.php
```

**Using Cookies:** If you already have a valid session ID, use the `-b` (cookie) flag to authenticate without re-entering a password.
```
curl -b 'PHPSESSID=c1nsa6op7vtk7kdis7bcnbadf1' http://<SERVER_IP>/dashboard.php
```
### 4. JSON and APIs

Modern web applications often use **JSON (JavaScript Object Notation)** to send data to the backend. When sending JSON via POST, you must explicitly tell the server what format you are using by setting the `Content-Type` header.

**Example cURL for a JSON API:**
```
curl -X POST -d '{"search":"london"}' \
     -H 'Content-Type: application/json' \
     -b 'PHPSESSID=c1nsa6op7...' \
     http://<SERVER_IP>/api/search.php
```

### 5. Browser DevTools: Storage & Console

- **Storage Tab (`Shift+F9`):** This is where you can view, edit, or delete cookies. In a security assessment, you might "hijack" a session by manually pasting a stolen cookie here and refreshing the page.
    
- **Console Tab:** You can use the `fetch()` API to trigger POST requests directly. By right-clicking a request in the **Network Tab** and selecting **Copy > Copy as Fetch**, you can quickly test how the backend reacts to modified JSON payloads right from the browser.
    

If a web application doesn't protect its cookies (e.g., missing `HttpOnly` or `Secure` flags), it may be vulnerable to **Session Hijacking** through attacks like XSS. Always check the cookie attributes in the Storage tab.

## CRUD APIs

Modern web applications often use APIs (Application Programming Interfaces) to interact with databases. These APIs follow the **CRUD** model, which maps specific HTTP methods to database operations.

### 1. The CRUD Model

CRUD stands for Create, Read, Update, and Delete. These are the four basic functions of persistent storage.

|**Operation**|**HTTP Method**|**Description**|
|---|---|---|
|**Create**|**POST**|Adds a new record/entry to the database.|
|**Read**|**GET**|Retrieves existing data from the database.|
|**Update**|**PUT / PATCH**|Modifies an existing record.|
|**Delete**|**DELETE**|Removes a record from the database.|

### 2. Interacting with API Endpoints

API endpoints often use a structured URL path to identify the table and the specific resource (row).

- **Example Structure:** `http://<IP>/api.php/[table]/[resource]`
    

#### Read (GET)

To retrieve data, we use a GET request. The response is typically returned in **JSON** format.

- **Tip:** Use the `jq` utility in Linux to "pretty-print" JSON output for better readability.
    

Bash

```
# Reading a specific city and formatting with jq
curl -s http://<SERVER_IP>/api.php/city/london | jq
```

#### Create (POST)

To add a new entry, we send a POST request with the data in the body. Because we are sending JSON, we must include the `Content-Type: application/json` header.

Bash

```
curl -X POST http://<SERVER_IP>/api.php/city/ \
     -d '{"city_name":"HTB_City", "country_name":"HTB"}' \
     -H 'Content-Type: application/json'
```

#### Update (PUT vs. PATCH)

- **PUT:** Used to replace the **entire** resource. If you only provide one field, the other fields in that row might be deleted or set to null, depending on the API design.
    
- **PATCH:** Used for **partial** updates (e.g., changing only the city name while leaving the country name intact).
    

Bash

```
# Updating 'london' to 'New_HTB_City'
curl -X PUT http://<SERVER_IP>/api.php/city/london \
     -d '{"city_name":"New_HTB_City", "country_name":"HTB"}' \
     -H 'Content-Type: application/json'
```

#### Delete (DELETE)

Deleting a resource is straightforward; you target the specific resource URL with the DELETE method.

Bash

```
curl -X DELETE http://<SERVER_IP>/api.php/city/New_HTB_City
```
### 3. Security Considerations

In a production environment, CRUD operations are protected by **Access Control**.

- **Authentication:** Users must typically provide a **Bearer Token (JWT)** or a **Session Cookie** to perform any action other than a simple Read.
    
- **Permissions:** Even if authenticated, a regular user should not have the permission to `DELETE` or `PUT` resources belonging to other users or administrative tables.
    
- **Vulnerabilities:** If an API allows a user to modify data they don't own, it is known as an **IDOR (Insecure Direct Object Reference)** vulnerability.
    

Use the `OPTIONS` method (`curl -X OPTIONS -i [URL]`) to see which HTTP methods the API endpoint supports before you start testing.
