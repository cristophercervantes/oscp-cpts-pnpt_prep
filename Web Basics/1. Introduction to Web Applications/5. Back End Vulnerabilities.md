## Common Web Vulnerabilities

When public exploits aren't available, penetration testers manually look for flaws in how an application handles logic, files, and data. Many of these are part of the **OWASP Top 10**, a standard awareness document for developers and security professionals.

### Broken Authentication & Access Control

These vulnerabilities strike at the heart of identity management.

- **Broken Authentication:** Flaws that allow an attacker to bypass the login process entirely.
    
    - _Example:_ Using a payload like `' or 0=0 #` in an email field to trick the database into thinking the login is always "True," allowing access without a password.
        
- **Broken Access Control:** Occurs when a user can access resources or perform actions outside of their intended permissions.
    
    - _Example:_ A regular student changing the URL from `/user/profile` to `/admin/panel` and successfully gaining administrative rights because the server failed to verify their role.
        
### Malicious File Upload

This occurs when an application allows users to upload files without strictly validating the file type or content.

- **The Risk:** An attacker can upload a web shell (e.g., a `.php` or `.asp` script). Once uploaded, they can navigate to the file's URL to execute OS commands on the server.
    
- **Bypassing Checks:** Even if filters are in place, attackers use techniques like "double extensions" (e.g., `image.php.jpg`) or null byte injections to trick the server into accepting a malicious script disguised as an image.
    
### Command Injection

Web applications sometimes need to run system-level commands (like `ping` or `curl`). If user input is included in these commands without sanitization, an attacker can "inject" their own commands.

- **How it works:** Attackers use shell operators like `;`, `&&`, or `|` to chain a second command to the legitimate one.
    
- **Example:** A tool that pings an IP address might run `ping [user_input]`. An attacker could input `8.8.8.8 | cat /etc/passwd` to force the server to reveal sensitive system files.
    
### SQL Injection (SQLi)

SQLi happens when user-supplied data is inserted into a database query in an unsafe way.

- **The Vulnerability:** If the code uses simple string concatenation like `"SELECT * FROM users WHERE name = '" + $input + "'"` , the attacker controls the query logic.
    
- **The Impact:** Attackers can bypass logins, extract the entire database (including password hashes), or in some configurations, gain full command execution on the database server.

# Public Vulnerabilities

## 1. Finding Public Vulnerabilities

The first step in assessing a web application is identifying its version. This version can often be found in the **source code** or specific files like `version.php` in open-source repositories.

Once a version is identified, researchers use several resources to find public exploits:

- **CVE (Common Vulnerabilities and Exposures):** Public records of patched vulnerabilities assigned a specific score.
    
- **Exploit Databases:** Online repositories like **Exploit DB**, **Rapid7 DB**, or **Vulnerability Lab**.
    
- **Critical Targets:** Penetration testers typically prioritize exploits with a CVE score of **8–10** or those that lead to **Remote Code Execution (RCE)**.
    
## 2. The Common Vulnerability Scoring System (CVSS)

CVSS is the industry standard for assessing the severity of security vulnerabilities. It allows organizations to prioritize their response to threats based on a numerical score.

### Scoring Metrics

A CVSS score is derived from three main groups:

1. **Base Score:** Represents the inherent characteristics of a vulnerability (0.0 to 10.0).
    
2. **Temporal Score:** Accounts for external events that change over time (e.g., the release of a public exploit).
    
3. **Environmental Score:** A customized metric based on the specific impact of the vulnerability on a particular organization.
    

### Severity Ratings

The National Vulnerability Database (NVD) provides Base scores using two versions:

|**Severity**|**CVSS v2.0 Range**|**CVSS v3.0 Range +1**|
|---|---|---|
|**None**|—|0.0|
|**Low**|0.0 – 3.9|0.1 – 3.9|
|**Medium**|4.0 – 6.9|4.0 – 6.9|
|**High**|7.0 – 10.0|7.0 – 8.9|
|**Critical**|—|9.0 – 10.0|

## 3. Back-End Server Vulnerabilities

Vulnerabilities are not limited to the web application itself but extend to plugins, web servers, and databases.

- **Web Servers:** These are highly critical because they are publicly accessible over the TCP protocol. A famous example is **Shell-Shock (2014)**, which allowed remote control over Apache servers via HTTP requests.
    
- **Internal Components:** Vulnerabilities in the operating system or database are often exploited _after_ an attacker has gained local access through an external flaw. These are frequently used for **Privilege Escalation** to gain higher-level control over the network.
    

Even if a vulnerability is not directly exploitable from the internet, it remains critical and must be patched to prevent the entire infrastructure from being compromised once a perimeter is breached.
