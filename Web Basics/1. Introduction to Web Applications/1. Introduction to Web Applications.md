# Web Applications - Introduction & Fundamentals

## What is a Web Application?

Web applications are **interactive programs** that run inside a web browser. They follow a **client-server architecture**:

- **Front-end (Client-side)**: What the user sees and interacts with (HTML, CSS, JavaScript)
- **Back-end (Server-side)**: The actual application logic, databases, and processing that runs on the server

Organizations can update and control the app centrally while making it accessible to anyone in the world.

**Common Examples**:

- Gmail
- Amazon
- Google Docs
- Any modern website with login, forms, dynamic content, etc.

> **Note**: Almost every website you use today is actually a web application (Web 2.0).

## Web Applications vs Traditional Websites

|Aspect|Traditional Websites (Web 1.0)|Web Applications (Web 2.0)|
|---|---|---|
|Content|Static|Dynamic|
|User Interaction|Very limited|Fully functional|
|Updates|Manual page editing|Real-time / server-side changes|
|Functionality|No real functions|Rich features & logic|

**Modern web apps are**:

- Modular
- Responsive (work on any screen size)
- Platform-independent

## Web Applications vs Native OS Applications

**Web Apps Advantages**:

- No installation required
- Run on any operating system (Windows, macOS, Linux, mobile)
- Single version for all users
- Easy & cheap to update (change once on the server)
- Zero space on user’s device

**Native Apps Advantages**:

- Faster performance
- Better access to hardware & OS libraries
- Deeper system integration

**Modern Trend**: Hybrid & Progressive Web Apps (PWAs) that combine the best of both worlds.

## Why Web Application Security Matters

Web apps are:

- Exposed to the entire internet
- Have a **huge attack surface**
- Often connected to databases containing sensitive data
- Frequently targeted by automated scanning tools

A single successful attack can lead to:

- Data breaches
- Financial loss
- Complete server compromise
- Business interruption

**Best Practice**: Regular web application penetration testing + secure coding from day one.

**Popular Testing Framework**: **OWASP Web Security Testing Guide**

### Typical Testing Approach

1. Review **Front-end** (HTML, CSS, JavaScript) → Look for XSS, Sensitive Data Exposure
2. Analyze **Back-end** functionality and server technologies
3. Test **Unauthenticated** and **Authenticated** perspectives (if login exists)

## Common Web Application Attacks & Real-World Impact

|Vulnerability|What It Allows|Real-World Example|
|---|---|---|
|**SQL Injection**|Extract data, read/write files, sometimes RCE|Pull AD usernames → Password spraying on VPN/O365|
|**File Inclusion**|Read source code, access hidden files/directories|Discover admin panels or config files|
|**Unrestricted File Upload**|Upload malicious files (webshells)|Gain full server control via profile picture upload|
|**Insecure Direct Object Reference (IDOR)**|Access other users’ data by changing IDs (e.g., /user/701 → /user/702)|View/edit another user’s profile or files|
|**Broken Access Control**|Privilege escalation during registration or actions|Change roleid=3 (user) to roleid=1 (admin) during signup|

# Web Application Layout & Architecture

No two web applications are the same. They differ in design, purpose, and infrastructure. Understanding the **layout**, **components**, and **architecture** helps us:

- Map the attack surface more effectively
- Identify where vulnerabilities may hide (code vs design flaws)
- Spot weak segmentation and access control issues
- Chain vulnerabilities across different layers

## Main Categories of Web Application Layout

Web applications can be broken down into three high-level categories:

1. **Web Application Infrastructure** – Physical/server setup (servers + databases)
2. **Web Application Components** – The building blocks (UI, Client, Server, Services)
3. **Web Application Architecture** – How all components relate and communicate

## 1. Web Application Infrastructure Models

These describe how servers and databases are organized.

### Common Infrastructure Models

|Model|Description|Security Level|Risk / Notes|
|---|---|---|---|
|**Client-Server**|Classic model: Browser (client) talks to Web Server (backend)|Medium|Most common|
|**One Server**|Everything (web app + database) on a **single server**|**Low**|"All eggs in one basket" – High risk|
|**Many Servers – One Database**|Multiple web servers share a single dedicated database server|Good|Better segmentation|
|**Many Servers – Many Databases**|Each app (or group) has its own database (or even own DB server)|**Best**|Strong isolation, good for redundancy|


> Other modern models: **Microservices** and **Serverless** architectures.

## 2. Web Application Components

Every web app is built from these core pieces:

- **Client** – Browser (where HTML, CSS, JS run)
- **Server**
    - Web Server (handles HTTP requests)
    - Web Application Logic (business rules, processing)
    - Database (stores data)
- **Services / Microservices** – Independent, task-specific components
- **Functions (Serverless)** – Code that runs without managing servers

## 3. Web Application Architecture (Three-Tier Architecture)

Most web apps follow a **3-tier/layer** design:

|Layer|What It Does|Technologies Involved|
|---|---|---|
|**Presentation Layer**|UI/UX – What the user sees and interacts with|HTML, CSS, JavaScript, Browser|
|**Application Layer**|Processes requests, checks authorization, business logic|Backend code (PHP, Python, Node.js, .NET, Java, etc.)|
|**Data Layer**|Stores and retrieves data|Databases (MySQL, PostgreSQL, MSSQL, MongoDB, etc.)|


Some web servers can also make direct OS calls (e.g., IIS ISAPI, PHP-CGI).

### Microservices Architecture

Think of microservices as **small, independent services** that do **one thing well**.

**Example** (Online Store):

- Registration service
- Search service
- Payment service
- Rating & Reviews service

**Benefits of Microservices**:

- Agility & faster development
- Flexible scaling
- Can use different programming languages
- Reusable code
- Better resilience (one service failing doesn’t take down everything)

**Downside**: More complex communication between services.

### Serverless Architecture

- No need to manage servers, scaling, or infrastructure
- Cloud providers (AWS Lambda, Azure Functions, Google Cloud Functions) handle everything
- Apps run in stateless containers (e.g., Docker)
- Pay only for actual usage

**Biggest advantage**: Developers focus on code, not servers.

## Architecture & Security Implications
- Many vulnerabilities come from **bad architecture/design**, not just bad code.
- Lack of proper **Role-Based Access Control (RBAC)** can allow users to access admin features or other users’ data.
- If you compromise a web server but can’t find the database → it’s probably on a **separate server**.
- Seeing only partial data? There may be **multiple databases**.

# Front End vs Back End

Web development is usually divided into two major parts:

- **Front End** → What the user sees and interacts with (Client-side)
- **Back End** → Everything that runs on the server (Server-side)

**Full Stack** development means working on both front end and back end.

Understanding this separation is crucial for penetration testers because vulnerabilities appear differently depending on which side we’re attacking.

## Front End (Client-Side)

The front end is everything that runs **inside the user’s browser**.

### What it includes:

- **HTML** – Structure and content (headings, paragraphs, forms, etc.)
- **CSS** – Styling, layout, colors, animations
- **JavaScript** – Interactivity, dynamic behavior, form validation, API calls

- Runs on the **client device** (browser)
- Must be **responsive** (work on mobile, tablet, desktop)
- Must work across different browsers and devices
- Poor front-end optimization can make the whole app feel slow (even if the server is fast)

### Other Front-End Responsibilities:

- Visual / Web Design
- User Interface (**UI**) Design
- User Experience (**UX**) Design
## Back End (Server-Side)

The back end is the “brain” of the web application. It handles all the heavy lifting that the user doesn’t see.

### Four Main Back-End Components:

|Component|Description|Common Examples|
|---|---|---|
|**Back-end Servers**|Hardware + Operating System that hosts everything|Linux, Windows, Docker containers|
|**Web Servers**|Handle HTTP requests from browsers|Apache, NGINX, IIS|
|**Databases**|Store and retrieve application data|MySQL, PostgreSQL, MSSQL, Oracle, MongoDB (NoSQL)|
|**Development Frameworks**|Tools used to build the core application logic|Laravel (PHP), Django (Python), Express (Node.js), Spring (Java), ASP.NET (C#)|

### Main Jobs of the Back End:

- Process business logic
- Handle authentication & authorization
- Communicate with the database
- Manage APIs for front-end communication
- Integrate with third-party services
- Store and protect sensitive data

Good practice is to run different components (web app, database) in separate **Docker containers** or even on separate servers for better security and stability.

## Securing Front End vs Back End

|Aspect|Front End|Back End|
|---|---|---|
|Where code runs|User’s browser|Server|
|Default access for tester|Usually visible (view source)|Hidden (unless open-source or LFI)|
|Testing type|Easier white-box if source available|Mostly black-box initially|
|Common attack vectors|XSS, Client-side logic flaws|SQL Injection, Command Injection, SSRF, etc.|


- Even if we can’t see the back-end code, the app can still be heavily exploited.
- **Injection attacks** (SQLi, Command Injection) often target the back end through user input.
- Some flaws (Local File Inclusion) can let us **read** back-end source code → turning black-box into white-box testing.

### Developer Mistakes (Top 20)

Here are the most critical mistakes that lead to real vulnerabilities:

1. Permitting invalid data into the database
2. Treating security as the last step
3. Storing passwords in plain text
4. Creating weak passwords
5. Storing unencrypted sensitive data
6. Over-relying on client-side validation
7. Trusting third-party code blindly
8. Hard-coding backdoor accounts
9. Failing to properly validate SQL queries
10. Remote File Inclusion vulnerabilities
11. Poor encryption practices
12. Ignoring proper logging and monitoring
13. Web Application Firewall misconfigurations ...and many more.

These mistakes commonly lead to the **OWASP Top 10** vulnerabilities:

### OWASP Top 10 

1. **Broken Access Control**
2. **Cryptographic Failures**
3. **Injection**
4. **Insecure Design**
5. **Security Misconfiguration**
6. **Vulnerable and Outdated Components**
7. **Identification and Authentication Failures**
8. **Software and Data Integrity Failures**
9. **Security Logging and Monitoring Failures**
10. **Server-Side Request Forgery (SSRF)**

> As penetration testers, we need to be able to **find, exploit, and clearly explain** these issues to clients.
