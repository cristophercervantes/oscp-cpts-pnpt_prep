# DNS

DNS translates domain names into IP addresses. You type `www.example.com`, DNS finds `192.0.2.1`. Without it you'd need to memorize IPs for every site.

## How a lookup works

1. Browser checks local cache first
2. Asks DNS resolver (usually your ISP)
3. Resolver asks a root name server → points to the right TLD server
4. TLD server (.com, .org etc.) → points to the authoritative name server
5. Authoritative server has the actual IP → sends it back
6. Resolver caches it, returns IP to your browser
7. Browser connects

## DNS Record Types

|Record|What it does|
|---|---|
|`A`|Domain → IPv4 address|
|`AAAA`|Domain → IPv6 address|
|`CNAME`|Alias pointing to another hostname|
|`MX`|Mail servers for the domain|
|`NS`|Authoritative name servers|
|`TXT`|Arbitrary text — SPF, DKIM, domain verification|
|`SOA`|Zone admin info (primary NS, serial number, TTL)|
|`SRV`|Hostname + port for specific services|
|`PTR`|Reverse lookup — IP → hostname|

## The hosts file

Local override for DNS. Checked before any DNS query.

- Windows: `C:\Windows\System32\drivers\etc\hosts`
- Linux/Mac: `/etc/hosts`

```
127.0.0.1       localhost
192.168.1.10    devserver.local
0.0.0.0         unwanted-site.com    # blocks a site
```

Edit with admin/root privileges. Changes take effect immediately.

## dig — the main tool

```bash
dig google.com                      # default A record lookup
dig google.com MX                   # mail servers
dig google.com NS                   # name servers
dig google.com TXT                  # TXT records
dig google.com ANY                  # all records (many servers ignore this)
dig @1.1.1.1 google.com             # query a specific DNS server
dig +trace google.com               # show full resolution path
dig -x 192.168.1.1                  # reverse lookup
dig +short google.com               # just the answer, no noise
dig +noall +answer google.com       # answer section only
```

Reading `dig` output:

- **Question section** — what was asked
- **Answer section** — the actual result + TTL
- **Footer** — query time, which server answered, message size

## What DNS can reveal

- **Subdomains** — NS, A, CNAME records reveal the full infrastructure
- **CNAME to old servers** — `dev.example.com CNAME oldserver.example.net` might point to something vulnerable
- **TXT records** — reveal third-party services (`_1password=...`, SPF includes, etc.)
- **New subdomains appearing** — `vpn.example.com` showing up means a new entry point
- **NS records** — tell you who's hosting, which affects your attack surface

## Subdomain enumeration

Subdomains often have dev/staging environments, admin panels, old apps, or exposed files that aren't linked anywhere publicly.

**Active (direct interaction):**

- Zone transfer attempts — rarely works but worth trying
- Brute force with wordlists

```bash
dnsenum --enum inlanefreight.com -f /usr/share/seclists/Discovery/DNS/subdomains-top1million-20000.txt -r
```

`-r` enables recursive brute-forcing (finds subdomains of subdomains).

**Passive (no direct contact):**

- Certificate Transparency logs (`crt.sh`) — SSL certs list SANs
- Google dorking with `site:` operator
- Online DNS aggregator databases

**Tools:**

|Tool|Good for|
|---|---|
|`dnsenum`|Full DNS enum + brute force + zone transfer attempts|
|`fierce`|Recursive subdomain discovery, easy to use|
|`dnsrecon`|Multiple techniques, flexible output|
|`amass`|Actively maintained, integrates many sources|
|`puredns`|Fast brute-forcing with good filtering|

# Virtual Hosts

One server, multiple websites. The web server figures out which site to serve based on the `Host` header in the HTTP request.

## VHosts vs Subdomains

- **Subdomain** — has a DNS record pointing to an IP
- **VHost** — a web server config entry. Might have a DNS record, might not

If a VHost has no DNS record, it's still reachable — just add it manually to your `/etc/hosts` file and point it at the server's IP. That's also why VHost fuzzing finds things that subdomain enumeration via DNS misses entirely.

## How it works

Browser sends `GET / HTTP/1.1` with `Host: dev.example.com` → web server checks its vhost config → finds a match → serves that site's files from its document root.

Same IP, different `Host` header = completely different website.

---

## Three types of virtual hosting

|Type|How it works|Common?|
|---|---|---|
|**Name-based**|Uses `Host` header to differentiate|Most common|
|**IP-based**|Each site gets its own IP|Expensive, less scalable|
|**Port-based**|Different ports for different sites|Uncommon, annoying for users|

Name-based is the standard. The other two exist but you'll rarely encounter them.

## VHost fuzzing with gobuster

```bash
gobuster vhost -u http://<target_IP> -w <wordlist> --append-domain
```

It sends requests with different `Host` headers and looks for non-404 responses.

Useful flags:

- `-t` — more threads, faster scan
- `-k` — ignore SSL/TLS cert errors
- `-o` — save output to file

Real example:

```bash
gobuster vhost -u http://inlanefreight.htb:81 \
  -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-110000.txt \
  --append-domain
```

Output:

```
Found: forum.inlanefreight.htb:81 Status: 200 [Size: 100]
```

`--append-domain` is required in newer gobuster versions — without it the full hostname doesn't get constructed correctly.

Other tools that do the same thing: **ffuf**, **feroxbuster**.

# Certificate Transparency Logs

Every SSL/TLS certificate issued by a CA gets logged in public CT logs — append-only, anyone can read them. That's the whole point: accountability and transparency.

For recon, this is gold. Every subdomain that ever got a certificate is in there, including old/expired ones that might still be running outdated software.

Brute-forcing is limited by your wordlist. CT logs are a historical record — if a cert was issued for `staging.internal.example.com`, it's in there even if it's not in any wordlist and has no public DNS record. You're not guessing, you're reading a ledger.

Also catches:

- Old subdomains with expired certs (potentially still running, possibly vulnerable)
- Wildcard certs that reveal the domain structure
- Subdomains issued right before a product launch or infrastructure change

## How to search CT logs

**crt.sh** — free, no account needed, quick

```bash
# All subdomains for a domain
curl -s "https://crt.sh/?q=facebook.com&output=json" | jq -r '.[] | .name_value' | sort -u

# Filter for only "dev" subdomains
curl -s "https://crt.sh/?q=facebook.com&output=json" \
  | jq -r '.[] | select(.name_value | contains("dev")) | .name_value' \
  | sort -u
```

Output example:

```
*.dev.facebook.com
dev.facebook.com
devvm1958.ftw3.facebook.com
secure.dev.facebook.com
```

**Censys** — more powerful, needs a free account. Better for filtering by IP, cert attributes, finding related infrastructure.

## The Merkle tree (why logs can't be tampered with)

CT logs use a Merkle tree structure. Each cert is a leaf node, hashed up through parent nodes to a single root hash. Change anything — even one byte in one cert — and the root hash changes, making tampering immediately obvious.

You don't need to understand the full math, just know that it's cryptographically tamper-evident by design. That's what makes CT logs trustworthy as a data source.
