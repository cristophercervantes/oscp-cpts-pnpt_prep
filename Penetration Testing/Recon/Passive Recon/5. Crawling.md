## Web Crawling (Spidering)

Automated process of mapping out a web application by systematically following links from one page to another. The bot starts at an initial seed URL, parses the HTML, pulls every link it finds, and drops them into a queue to repeat the cycle iteratively.

- **Crawling vs. Fuzzing:** Crawling maps the application based on paths that _explicitly exist_ and are linked in the code. Fuzzing blindly guesses or brute-forces directories based on a wordlist.
    

### Traversal Strategies

- **Breadth-First:** Explores the width of the site structure first. It hits all links on the homepage before moving to deeper layers. Best for a fast, high-level structural map.
    
- **Depth-First:** Explores depth first. It follows a single link chain as deep as it goes before backtracking to try another path. Best when hunting down deeply nested components or specific hidden content.
    

## High-Value Data Points

When running a crawler on a target, the goal is to extract specific pieces of information to expand the attack surface:

- **Internal & External Links:** Maps out the architecture and reveals dependencies or relationships with third-party domains.
    
- **Developer Comments:** Inline comments in code, blogs, or forums frequently leak internal workflows, software details, or accidental hints about application logic.
    
- **Metadata:** Page titles, descriptions, author details, and timestamps that help establish the context and age of the underlying infrastructure.
    
- **Exposed Files:** Crawlers can be tuned to flag dangerous files left public, such as backup copies (`.bak`, `.old`), configurations (`web.config`, `settings.php`), or server logs (`error_log`). These routinely leak raw database credentials, source snippets, or API tokens.
    

## Data Correlation & Attack Chains

Individual data points are rarely useful on their own; threat modeling requires aggregating small pieces of information to uncover a systemic flaw.

- **Example 1 (Directory Discovery):** A crawler logs several links referencing a `/files/` directory. While the individual URLs seem benign, looking at the pattern prompts a manual check, revealing that directory browsing is enabled and exposing raw backup archives.
    
- **Example 2 (Contextual Validation):** A stray source code comment mentions an internal "file server". By itself, the comment is low-risk. Combined with the discovery of the open `/files/` directory, it validates that the exposed server is likely hosting sensitive internal documentation.

## `robots.txt` 

The `robots.txt` file is a plain text document placed in the root directory of a web server (e.g., `https://example.com/robots.txt`). It implements the **Robots Exclusion Standard**, functioning as an advisory protocol or "etiquette guide" dictating which directories and files automated crawlers are allowed or forbidden to index.

`robots.txt` is entirely client-side and completely unenforceable. A malicious crawler or threat actor can choose to ignore it entirely.

## File Structure & Directives

The file consists of discrete blocks of records separated by blank lines. Each block specifies target crawlers followed by instructions.

### Components

- **User-agent:** Identifies the specific bot the rules apply to.
    
    - `User-agent: *` targets all bots universally (wildcard).
        
    - `User-agent: Googlebot` targets Google's spider specifically.
        

### Directives

|**Directive**|**Purpose**|**Technical Example**|
|---|---|---|
|**`Disallow`**|Blocks paths or pattern matching from indexing.|`Disallow: /admin/`|
|**`Allow`**|Overrides a broader `Disallow` rule for a specific sub-path.|`Allow: /public/`|
|**`Crawl-delay`**|Dictates a pause (in seconds) between sequential requests to prevent server exhaustion.|`Crawl-delay: 10`|
|**`Sitemap`**|Points directly to an XML sitemap file to expedite structured mapping.|`Sitemap: https://site.com/sitemap.xml`|

## Defensive & Operational Intent

Legitimate web scraping operations and search engine indices obey these boundaries to maintain stability:

- **Server Resource Preservation:** Stops aggressive crawlers from hammering application backends and database infrastructure.
    
- **SEO Management:** Prevents low-value, duplicate, or internal utility pages from muddying public search results.
    

## Offensive Reconnaissance Value

From a penetration testing or threat assessment perspective, `robots.txt` functions as an unintentional blueprint of high-value targets.

### 1. Attack Surface Enumeration

Developers frequently utilize `Disallow` to hide sensitive functionality from Google, ironically creating a public list of interesting targets for security analysts. These entries commonly leak:

- Administrative portals (`/admin/`, `/backend/`)
    
- Staging environments or development setups (`/dev/`, `/test/`)
    
- Hidden configuration paths or user panel interfaces
    

### 2. Structural Mapping

Analyzing the structural variance between allowed and disallowed paths helps construct a baseline architectural layout of the site, exposing components completely decoupled from the public-facing navigation menus.

### 3. Honeypots & Crawler Traps

Blue teams occasionally inject dummy directories into `robots.txt` that are completely unlinked anywhere else on the actual web application. If a source IP hits a directory restricted by `Disallow: /honey-pot/`, security operations center (SOC) systems instantly flag that client as a malicious or non-compliant scanner.

## Log Analysis Example

```
User-agent: *
Disallow: /admin/
Disallow: /private/
Allow: /public/

User-agent: Googlebot
Crawl-delay: 10
Sitemap: https://www.example.com/sitemap.xml
```

- **Recon Intel:** All automated spiders are requested to drop connections to `/admin/` and `/private/`. A penetration tester now has two immediate, highly sensitive directory targets verified to exist on the filesystem.
    
- **Scraping Footprint:** Googlebot is throttled to 1 request every 10 seconds, while an XML map file is cleanly exposed to easily download the complete path structure of the application.

# Well-Known URIs

`/.well-known/` is a standardized directory on web servers where sites put config files, metadata, and security info. Defined in RFC 8615, maintained by IANA.

For recon, just browse to `https://target.com/.well-known/` and see what's there.

## Useful ones to check

|URI|What's in it|
|---|---|
|`/.well-known/security.txt`|Contact info for reporting vulns — also reveals security team details|
|`/.well-known/openid-configuration`|Full OAuth/OpenID Connect config — endpoints, algorithms, supported scopes|
|`/.well-known/change-password`|Where the password change page is|
|`/.well-known/assetlinks.json`|Domain-to-app ownership verification|
|`/.well-known/mta-sts.txt`|Email security policy|

## openid-configuration — the interesting one

If the target uses OAuth/OpenID Connect, this endpoint dumps the entire auth config:

```
https://example.com/.well-known/openid-configuration
```

Returns JSON like:

```json
{
  "issuer": "https://example.com",
  "authorization_endpoint": "https://example.com/oauth2/authorize",
  "token_endpoint": "https://example.com/oauth2/token",
  "userinfo_endpoint": "https://example.com/oauth2/userinfo",
  "jwks_uri": "https://example.com/oauth2/jwks",
  "scopes_supported": ["openid", "profile", "email"]
}
```

What this gives you:

- All auth-related endpoints in one place
- `jwks_uri` — the cryptographic keys used for token signing
- Supported algorithms — useful for understanding what attacks might apply
- Scopes — what data the app can request about users

# Web Crawling

Crawlers automatically map out a site — following links, pulling content, finding things that aren't obviously linked anywhere. Useful for finding emails, hidden pages, JS files, comments left in source code, and form endpoints.

## Tools

|Tool|When to use it|
|---|---|
|Burp Suite Spider|Already in Burp, good for app testing workflows|
|OWASP ZAP Spider|Free alternative, automated + manual modes|
|Scrapy|Python framework, build custom spiders for specific needs|
|Apache Nutch|Large-scale crawls, overkill for most pentest recon|

## ReconSpider (Scrapy-based)

```bash
pip3 install scrapy

wget -O ReconSpider.zip https://academy.hackthebox.com/storage/modules/144/ReconSpider.v1.2.zip
unzip ReconSpider.zip

python3 ReconSpider.py http://inlanefreight.com
```

Outputs `results.json` with:

|Key|What's in it|
|---|---|
|`emails`|Email addresses found on the site|
|`links`|All internal links|
|`external_files`|PDFs and other files linked externally|
|`js_files`|JavaScript files — useful for finding hidden endpoints|
|`form_fields`|Any forms on the site|
|`images`|Image URLs|
|`comments`|HTML comments in source — devs leave things here|

The interesting ones for recon: **emails** (social engineering targets), **js_files** (hardcoded API keys, endpoints), **comments** (dev notes, internal paths, version info).
