# VPS
A **Virtual Private Server (VPS)** is an isolated, virtualized environment created on a physical server. It functions as **Infrastructure-as-a-Service (IaaS)**, providing the control of a dedicated server at a fraction of the cost. By using a hypervisor to partition a single physical machine into multiple "virtual" ones, providers can offer dedicated resources (CPU, RAM, Storage) to each user.

### 1. The Middle Ground of Hosting

A VPS is often described as the "Goldilocks" solution between Shared Hosting and Dedicated Servers:

- **Shared Hosting:** Inexpensive but risky, as other users' traffic spikes or security breaches can affect your site.
    
- **Dedicated Server:** High performance and total control, but very expensive and requires significant hardware management.
    
- **VPS:** Offers **encapsulation**. Your OS is hidden from others on the same hardware, meaning if a neighbor's site crashes or is hacked, your environment remains stable and secure.
    
### 2. Common Use Cases

Because you have "root" or "administrator" access to the OS, a VPS is highly versatile. Common deployments include:

- **Infrastructure:** Web servers (LAMP/WAMP), Mail servers, and DNS servers.
    
- **Development:** Hosting code repositories (Git) or acting as a staging environment for testing applications.
    
- **Security & Networking:** Running **VPNs**, **Proxy servers**, or acting as a **Command & Control (C2)** server for red team operations.
    
- **Gaming:** Hosting private servers for multiplayer games.
    
### 3. Operating System Considerations

Most providers allow you to choose between various flavors of **Linux** (Ubuntu, Debian, CentOS) or **Windows Server**.

- **Cost Factor:** Windows VPS instances often carry a higher monthly fee (sometimes double) due to licensing costs, whereas Linux is open-source and typically cheaper.
    
- **Management:** Linux is usually managed via SSH (CLI), while Windows servers are managed via Remote Desktop (RDP).

## Setting Up a VPS (Linode Example)

A VPS is a critical asset for penetration testing, acting as a persistent base for tools, data exfiltration, and hosting services like C2 (Command & Control). While this example uses **Linode**, the workflow is nearly identical across providers like DigitalOcean or AWS.

### 1. Provisioning the Server

When creating a "Linode" (instance), you must define the following parameters:

- **Location:** Choose a data center geographically closest to you to minimize latency (ping). For specific regional tests, you can provision a VPS in that target's continent.
    
- **Plan:** For most security tasks, a **Shared CPU** instance is sufficient.
    
- **Resources:** 1GB of RAM is fine for simple scripts, but if you are running heavy services (like a full security stack or multiple Docker containers), you should scale to 2GB or higher.
    
- **Operating System:** Options usually include Ubuntu, Debian, or specialized distros. Since you are familiar with ParrotOS (Debian-based), a Debian/Ubuntu image is a natural choice.
    

### 2. Securing Access with SSH Keys

While you can log in with a root password, using **SSH Key Pairs** is the industry standard for security. It involves two files:

1. **Private Key (`vps-ssh`):** Stored on your local machine. **Never share this.**
    
2. **Public Key (`vps-ssh.pub`):** Uploaded to the VPS.
    

**Generating the keys locally:**
```
# Using Ed25519 for better security and performance
ssh-keygen -t ed25519 -f vps-ssh
```

### 3. Initial Configuration & User Management

Running everything as the `root` user is a major security risk. If one of your hosted services is compromised, the attacker immediately has full system control.

**Steps to set up a safe environment:**

1. **Create a new user:** `adduser <username>`
    
2. **Grant Sudo privileges:** `usermod -aG sudo <username>`
    
3. **Deploy SSH Key:** Manually add your public key to the new user's authorized list:
    ```
    mkdir ~/.ssh
    echo 'ssh-ed25519 AAAAC3...' > ~/.ssh/authorized_keys
    chmod 600 ~/.ssh/authorized_keys
    ```
    
### 4. Connecting to the VPS

Once configured, you can log in securely using your private key without typing a password every time.
```
# The -i flag specifies the identity file (private key)
ssh <username>@<vps-ip-address> -i vps-ssh
```

### **Server Management Best Practices 

When setting up and managing a remote server, the priority order should be:

1. **Security** (especially access control)
2. **Performance & Reliability**
3. **Ease of management**

The recommended approach is to **start with strong access control** first, then add services. This prevents accidentally leaving insecure entry points open.

#### **1. Hardening SSH Access (Most Important Step)**

Never leave a server accessible with password login. The best practice is:

- Disable root login
- Disable password authentication
- Use **SSH key authentication** only
- Change the default SSH port (from 22 to something else)
- Restrict access to specific users

**Example secure sshd_config changes** (/etc/ssh/sshd_config):
```
PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
X11Forwarding no
Port 4444                  # Change from default 22
AllowUsers cry0l1t3        # Only allow this user
```

After editing, restart SSH:
```
sudo service ssh restart
```

#### **2. SSH Key Generation & Management**

Generate a strong key (ED25519 is currently one of the best):
```
ssh-keygen -t ed25519 -f ~/.ssh/cry0l1t3
```

**Steps after generating the key:**

1. Copy the **public key** (.pub file) to the server’s ~/.ssh/authorized_keys
2. Set correct permissions:
    ```
    chmod 600 ~/.ssh/authorized_keys
    ```
    
3. Add the private key to the SSH agent:
    ```
    ssh-add ~/.ssh/cry0l1t3
    ```
    

**Create SSH config** (~/.ssh/config) for easier connections:
```
Host MyVPS
    HostName <IP or domain>
    IdentityFile ~/.ssh/cry0l1t3
    Port 4444
    User cry0l1t3
    IdentitiesOnly yes
```

Then connect simply with:
```
ssh MyVPS
```

**Start SSH agent** (add to ~/.bashrc or ~/.zshrc for auto-start):
```
eval $(ssh-agent)
```

#### **3. Password & Secret Management**

Never reuse passwords. Use a **password manager** to generate and store strong, unique passwords and secrets.

Recommended options:

- **Proton Pass**
- **Bitwarden**
- **1Password**
- **Passbolt** (self-hosted, uses GPG)
- **Psono**
- **Passky**
- **OpenBao**

Most of these offer **end-to-end encryption (E2EE)**, meaning even the service provider cannot read your data.

#### **4. Git Hosting for Configuration & Dotfiles**

**Git** is excellent not just for code, but for managing your own server configurations (dotfiles).

Benefits:

- Version control of your configs
- Easy rollback if something breaks
- Quick setup of new servers by cloning a repo
- Supports CI/CD workflows

Popular Git platforms:

- **GitHub**
- **GitLab**
- **Bitbucket**
- **Gitea** (lightweight, self-hostable)
- **OneDev**

Many cloud providers (like Linode) offer pre-configured marketplace images for both password managers and Git hosting.

### **Network Security 

Network security is one of the **most important** parts of cybersecurity. This is where we define who can access what. Once the rules are set properly, the main job becomes monitoring and keeping everything hardened.

Because we want both **strong security** and **good efficiency**, we need a modern, easy-to-manage solution for giving remote access to our servers.

#### **Modern Solution: Zero Trust Network Access (ZTNA)**

Traditional VPNs give broad access once you're inside the network — which is risky. **ZTNA** follows the principle: **"Never Trust, Always Verify"**

- Every user, device, and connection is checked individually based on:
    - Identity
    - Context
    - Device health
    - Security status
- You only get access to **specific resources** (very granular control)

**Popular ZTNA Tools:**

- **Netbird**
- **Tailscale**
- **Twingate**

Each has a slightly different focus:

- **Netbird** → Best for teams who want **simple + automated** setup. Great for hybrid/cloud + on-prem environments. **Fully open-source** and can be **self-hosted**.
- **Tailscale** → Super easy, minimal config. Perfect for remote employees accessing internal services or simple site-to-site connections.
- **Twingate** → Strong for complex environments (databases, Kubernetes, legacy apps) in multi-cloud setups.
### **Netbird

#### **Step-by-Step Setup**

1. **Register on Netbird**
    
    - Go to Netbird’s website and create a free account.
    - Verify your email → you’ll land on the **Dashboard**.
2. **Dashboard View**
    
    - Shows all connected **Peers** (devices)
    - Columns: Peer Name, Internal IP, Domain Name, Last Seen, OS, Client Version
3. **Add Your VPS to the Network**
    
    - Go to **Setup Keys** → Click **Create Setup Key**
    - Give it a name → Copy the generated key
4. **Install Netbird Client on the VPS (Ubuntu example)**
```
curl -fsSL https://pkgs.netbird.io/install.sh | sh
```

- Enter your sudo password when asked.
- After installation, run:
```
netbird up --setup-key YOUR-SETUP-KEY-HERE
```

- You should see: **"Connected"**

5. **Verify the Connection**
    
    - Netbird creates a new interface called **wt0**
```
ifconfig wt0
# or
ip addr show wt0
```

- You’ll see an internal IP (something like 100.108.x.x)

6. **Approve the Peer**
    - Go back to the Netbird Dashboard.
    - The new VPS peer will appear → **Approve** it.
    - (Even if someone steals the setup key, they still need admin approval)
7. **Test SSH Access**
```
ssh cry0l1t3@myvps.netbird.cloud
```

- You can now connect using the Netbird domain or internal IP.

### **Harden the Firewall 
After confirming the connection works, **lock down** the server so it only accepts connections through the Netbird interface (wt0).

```
# Reset UFW
ufw --force reset

# Allow everything on wt0 interface
ufw allow in on wt0

# Default policies
ufw default deny incoming
ufw default allow outgoing

# Enable firewall
ufw --force enable

# Check status
ufw status
```

### **Extra Hardening: Make SSH Listen Only on wt0**

You can run this script to force SSH to listen **only** on the Netbird interface (recommended):
```
#!/bin/bash

# Get wt0 IP
WT0_IP=$(ip addr show wt0 | grep -oP 'inet \K[\d.]+')

# Backup sshd_config
cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak_$(date +%F_%H-%M-%S)

# Set ListenAddress to wt0 IP only
sed -i '/^ListenAddress /d' /etc/ssh/sshd_config
echo "ListenAddress $WT0_IP" >> /etc/ssh/sshd_config

# Test and restart
sshd -t && systemctl restart sshd && echo "SSH hardened successfully!"
```

## SSH Hardening

SSH is always installed on the VPS, giving us guaranteed access to the server in advance. Now we can change some of the settings in the configuration file `/etc/ssh/sshd_config` to enforce these security measures for our SSH server.

#### Install Fail2Ban
```
cry0l1t3@MyVPS:~$ sudo apt install fail2ban -y
```

Once we have installed it, we can find the configuration file at `/etc/fail2ban/jail.conf`. We need to make a copy of this file to prevent our changes from being overwritten during updates.

#### Fail2Ban Config Backup
```
cry0l1t3@MyVPS:~$ sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local
```
In this file, we will find the field commented out with `# [sshd]`. In most cases, we will find the first line commented out there. Otherwise, we add this and two more, as shown in the following example:

#### /etc/fail2ban/jail.local
```
...SNIP... 
# [sshd] 
enabled = true 
bantime = 4w 
maxretry = 3
```

With this, we enable monitoring for the SSH server, set the `ban time` to four weeks, and allow a maximum of 3 `attempts`. The advantage of this is that once we have configured our `2FA` feature for SSH, fail2ban will ban the IP address that has entered the `verification code` incorrectly three times too. We should make the following configurations in the `/etc/ssh/sshd_config` file:

#### Editing OpenSSH Config
```
cry0l1t3@MyVPS:~$ sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak cry0l1t3@MyVPS:~$ sudo vim /etc/ssh/sshd_config
```
